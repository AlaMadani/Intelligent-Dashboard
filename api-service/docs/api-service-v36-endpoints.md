# API Service V3.6.1 Endpoints

`api-service` is a **read-side only** Spring Boot API. It reads V3.6.1 Redis snapshots and SQL Server rows written by `dataprocessor`, exposes REST/SSE to the Quasar frontend, and calls the configured LLM provider only on explicit explanation requests.

**It does not:**
- Run ML inference, rebuild feature vectors, or recompute risk
- Finalize sessions or deduplicate source data as business logic
- Consume raw Kafka scoring events or call `dataprocessor` directly
- Own database migrations

Source deduplication belongs to `dataprocessor`. api-service may apply read-side eventId-based dedup as a defensive measure, logging warnings when duplicates are encountered.

## Response Envelope

All controller responses use the existing `ApiResponse<T>` envelope. Frontend code should read business fields from `response.data`, not from the response root.

Unless a response example is explicitly labeled **Full response body**, examples in this document show the `data` payload only for readability.

The actual response body shape is:

```json
{
  "data": {
    "schemaVersion": "v3.6.1"
  },
  "meta": null
}
```

## V3.6.1 Pagination

V3.6.1 list endpoints currently return pagination fields inside `data`, not in `ApiResponse.meta`.

Actual list response shape:

```json
{
  "data": {
    "schemaVersion": "v3.6.1",
    "items": [],
    "limit": 100,
    "offset": 0,
    "count": 0,
    "hasMore": false
  },
  "meta": null
}
```

The legacy endpoints such as `/api/v1/sessions` and `/api/v1/anomalies` continue to use the older `ApiResponse.meta` pagination structure.

## ID Conventions

- V3.6.1 alert endpoints use `eventId`: `GET /api/v1/alerts/{eventId}`.
- Legacy anomaly endpoints use the SQL database numeric anomaly id: `GET /api/v1/anomalies/{id}`.
- V3.6.1 live alert and investigation DTOs include `eventId` and, when the payload came from SQL or already contains it, `id` and `anomalyDbId`.
- Redis alert snapshots may not contain `id/anomalyDbId` unless `dataprocessor` writes them. SQL fallback responses do include them.
- Frontend routing rule: use `/alerts/{eventId}` for the V3.6.1 investigation view; use `/anomalies/{id}` only for legacy screens.

## Source and Warnings

All V3.6.1 dashboard endpoints now include a `source` field indicating data provenance. Recommended source values:

| Source | Meaning |
|--------|---------|
| `redis` | Fresh snapshot from Redis (primary) |
| `sql_fallback` | Fallback from `dashboard_snapshots` or `llm_explanations` SQL table |
| `sql` | Legacy SQL row from `anomaly_events` / `session_analysis` |
| `sql-payload` | Deserialized from investigation/evidence JSON stored in SQL |
| `generated_fallback` | Neither Redis nor SQL had data; computed default |
| `generated` | Freshly generated by active LLM provider (POST explanation with `forceRefresh=false`) |
| `force_generated` | Generated with `forceRefresh=true`, bypassing all caches |
| `provider_error_fallback` | Active LLM provider returned an error; local heuristic used instead (not cached) |

Source/warning metadata is available where the frontend most needs degraded/fallback banners:

- **Dashboard views** (security-overview, churn, forecast, runtime-health): `source` field at the response root; warnings in applicable fields (`fieldCoverageWarnings`, `forecastWarnings`).
- **Alert list items**: `source` is `redis`, `sql_fallback`, or `sql`; `warnings` is an array.
- **Alert investigation**: `source` is `redis`, `sql-payload`, `sql`, or `sql_fallback`; `warnings` is an array; `runtimeWarnings` contains runtime-specific model warnings.
- **Runtime health**: `source` indicates Redis, SQL `model-health` snapshot, or `generated_fallback` when both miss.
- **User 360 SQL fallback**: includes `source: "sql_fallback"` and a `warning` field documenting that historical rows may contain pre-correction data.

## Live Alerts

`GET /api/v1/alerts/live?riskLevel=CRITICAL&limit=100`

Reads `alerts:live:v3_6` from Redis first, then falls back to SQL `dashboard_snapshots` with `view_name=alerts` / `snapshot_key=alerts:latest`, then falls back to SQL `anomaly_events`.

### Deduplication

SQL fallback rows from `dashboard_snapshots` may contain duplicate `eventId` entries with different completeness levels (the dataprocessor may write multiple rows per event across snapshot refreshes). The API deduplicates by `eventId` using a richness score — the row with the most populated fields (timestamp, riskLevel, eventAction, model scores, etc.) per eventId is kept.

### Hydration from stored payloads

After deduplication, if any of these fields are still missing:

`timestamp`, `eventAction`, `apiTemplate`, `apiFamily`, `controller`, `page`, `country`, `device`, `browser`, `os`, `httpMethod`, `status`, `anomalyTypeConfidence`, `xgboostAnomalyScore100`, `lightgbmAlertScore100`, `transformerRiskScore100`, `tcnRiskScore100`, `modelContributions`, `llmEvidencePayloadAvailable`

the API hydrates them from richer stored payload sources in this order:

1. `anomaly_events` SQL row columns (eventTime for timestamp, eventJson for event metadata, model score columns, modelContributionsJson)
2. Stored investigation payload (`investigation_payload_json`) — provides full eventMetadata, modelScores, modelContributions, triggeredRules
3. LLM evidence payload (`llm_explanation_evidence_payload_json`) — provides modelScores, modelContributions, eventMetadata, llmEvidencePayloadAvailable

Non-null values are never overwritten with null. A debug log `ALERT_LIVE_ROW_HYDRATED` is emitted per hydrated row listing the eventId and field names.

### Risk level fallback

If `riskLevel` is null but `finalRiskScore` is available, risk level is computed server-side using dataprocessor thresholds:
- `>= 80` → `CRITICAL`
- `>= 60` → `HIGH`
- `>= 35` → `MEDIUM`
- `< 35` → `LOW`

If both are null, `"Risk level unavailable"` is added to `warnings`.

Items from the dashboard_snapshot fallback have `source: "sql_fallback"`.

## Alert Investigation

`GET /api/v1/alerts/{eventId}`

Reads `alert:investigation:{eventId}` from Redis first, then SQL `investigation_payload_json` from `anomaly_events` and `session_analysis`, then builds a detail response from stored SQL fields.

**Evidence hydration**: When the investigation response is missing evidence fields (`sequenceEvidence`, `tabularEvidence`, `ruleEvidence`, `churnContext`, `forecastContext`, `anomalyTypeAttribution`, `modelScores`, `modelContributions`), the API attempts to hydrate them from the LLM evidence payload (`alert:llm-evidence:{eventId}` or SQL `llm_explanation_evidence_payload_json`). `eventMetadata` is hydrated from evidence only if the detail's `eventMetadata` is null and the evidence contains an `eventMetadata` field. If `eventMetadata` is already present (from Redis or SQL `event_json`), it is preserved unchanged. `eventMetadata` is **never** mapped from `evidence.risk`.

The response includes `sessionLifecycle` metadata when available from Redis or SQL payload. Both source shapes are supported:
- **Nested:** `payload.sessionLifecycle` as an object containing `sessionEndReason`, `sessionEndedExplicitly`, `sessionEndedAt`, `sessionDurationMs`, `sessionEventCount`
- **Flat:** individual fields at the payload root: `sessionEndReason`, `sessionEndedExplicitly`, `sessionEndedAt`, `sessionDurationMs`, `sessionEventCount`

SQL fallback preserves session lifecycle fields, runtimeWarnings, modelScores/modelContributions, and triggeredRules from the investigation payload without overwriting with null when Redis has richer data.

## LLM Evidence

Lookup order:

1. Redis key `alert:llm-evidence:{eventId}`

## LLM Explanation

### GET — Cached explanation (no LLM call)

`GET /api/v1/explanations/alerts/{eventId}`

Lookup order:

1. Redis key `ai:explanation:v3_6:alert:{eventId}:latest`
2. SQL `llm_explanations` table (latest current row by `eventId`)

If SQL hit, rehydrates Redis. If both miss, returns 404 `EXPLANATION_NOT_FOUND`.

**This endpoint never calls the LLM provider.**

### POST — Generate explanation

`POST /api/v1/explanations/alerts/{eventId}`

Request body (all fields optional):

```json
{
  "forceRefresh": false,
  "style": "security_analyst",
  "language": "en",
  "includeRecommendedActions": true
}
```

#### Behavior when `forceRefresh=false`

1. Check Redis `ai:explanation:v3_6:alert:{eventId}:latest`
2. If Redis hit → return `source=redis`, `cached=true`. Do NOT call LLM.
3. If Redis miss → check SQL `llm_explanations` (latest current row)
4. If SQL hit → return `source=sql_fallback`, `cached=true`, rehydrate Redis. Do NOT call LLM.
5. If both miss → load evidence payload from Redis/SQL
6. If evidence unavailable → 404 `EVIDENCE_NOT_FOUND`. Do NOT call LLM.
7. If evidence available → call active LLM provider (default `nvidia-nim`)
8. Store generated explanation in Redis (`:*evidenceHash*:style:language` and `:latest`) and SQL (`llm_explanations`)
9. Return `cached=false`, `source=generated`

#### Behavior when `forceRefresh=true`

1. Bypass both Redis and SQL cached explanation lookup (still reads evidence)
2. Load evidence payload from Redis first, SQL fallback
3. If evidence unavailable → 404 `EVIDENCE_NOT_FOUND`. Do NOT call LLM.
4. If evidence available → call active LLM provider (default `nvidia-nim`)
5. Overwrite/update Redis cache (both specific and latest keys)
6. SQL: mark previous current row as `is_current=false`, insert new row with `is_current=true`
7. Response: `cached=false`, `source=force_generated`, `forceRefresh=true`

#### Token waste prevention

| Scenario | LLM called? | Log line |
|----------|-------------|----------|
| Redis cache hit (`forceRefresh=false`) | No | `LLM_EXPLANATION_CACHE_HIT source=redis` |
| SQL cache hit (`forceRefresh=false`) | No | `LLM_EXPLANATION_CACHE_HIT source=sql_fallback` |
| Cache miss + evidence exists | Yes | `LLM_EXPLANATION_GENERATE` |
| `forceRefresh=true` + evidence exists | Yes | `LLM_EXPLANATION_FORCE_GENERATE` |
| No evidence available | No | `LLM_EXPLANATION_SKIPPED_NO_EVIDENCE` |
| Generation complete | — | `LLM_EXPLANATION_STORED` |

#### Concurrency protection

A Redis lock (`lock:llm-explanation:{eventId}:{language}:{style}`) prevents duplicate simultaneous generations:
- If `forceRefresh=false` and lock is held, retry cache lookup once; if still miss, return 409 `GENERATION_IN_PROGRESS`
- If `forceRefresh=true` and lock is held, return 409 `GENERATION_IN_PROGRESS`

#### Source values

| Source | Meaning |
|--------|---------|
| `redis` | Returned from Redis cache (GET or POST with cache hit) |
| `sql_fallback` | Returned from SQL `llm_explanations` with Redis rehydration |
| `generated` | Freshly generated by active LLM provider |
| `force_generated` | Generated with `forceRefresh=true`, bypassing all caches |
| `provider_error_fallback` | LLM provider returned an error; local heuristic returned (not cached in Redis/SQL) |

#### SQL persistence

Generated explanations are persisted in the `llm_explanations` table. History is preserved:
- On new generation, the previous current row (`is_current=true`) for matching `eventId`+`language`+`style`+`include_recommended_actions` is marked `is_current=false`
- A new row is inserted with `is_current=true`
- Cache key includes `evidenceHash`, so if evidence changes, old cached explanations are not reused silently
- Evidence hash resolution: if the evidence payload contains an `evidenceHash` field (set by the dataprocessor as full 64-char SHA-256), it is used as-is. If absent, the API computes a 16-char truncated SHA-256 from the serialized evidence JSON

#### Provider configuration

The active LLM provider is selected by `app.llm.provider` (default: `nvidia-nim`). Both NVIDIA NIM and Gemini providers are bundled.

| Property | Default | Description |
|----------|---------|-------------|
| `app.llm.provider` | `nvidia-nim` | Active provider name (`nvidia-nim` or `gemini`) |
| `app.llm.nvidia.base-url` | `https://integrate.api.nvidia.com/v1` | NVIDIA NIM API base URL |
| `app.llm.nvidia.api-key` | `${NVIDIA_API_KEY}` | NVIDIA NIM API key (env var) |
| `app.llm.nvidia.model` | `nvidia/nemotron-3-super-120b-a12b` | Model ID, configurable to any NVIDIA model |
| `app.llm.nvidia.temperature` | `1.0` | Generation temperature |
| `app.llm.nvidia.top-p` | `0.95` | Top-p sampling |
| `app.llm.nvidia.max-tokens` | `1800` | Max output tokens |
| `app.llm.nvidia.timeout-ms` | `120000` | HTTP request timeout |
| `app.llm.nvidia.enable-thinking` | `false` | Enable thinking/reasoning mode (only applies when `include-extra-body=true`) |
| `app.llm.nvidia.reasoning-budget` | `1024` | Token budget for reasoning (only applies when `include-extra-body=true`) |
| `app.llm.nvidia.include-extra-body` | `false` | Include NVIDIA-specific top-level fields (`chat_template_kwargs`, `reasoning_budget`). When `false`, sends only OpenAI-standard fields |
| `app.llm.nvidia.minimal-request-mode` | `false` | Diagnostic mode: sends a single user message `"Say hello in one sentence."` ignoring evidence. When `true`, excludes all extra fields regardless of `include-extra-body` |
| `app.llm.nvidia.log-request-json` | `false` | Logs a sanitized request body summary (`LLM_PROVIDER_REQUEST_BODY`) with roles, content lengths, and present fields. Does not log the API key |

Set `NVIDIA_API_KEY` environment variable with a valid NVIDIA API key. If the key is missing, the provider returns a `NOT_CONFIGURED` error and the service falls back to heuristic explanation.

##### Prompt design

NVIDIA Nemotron receives a **structured two-message prompt**:

| Message | Content |
|---------|---------|
| **System** | Senior cybersecurity analyst role definition with strict rules — no invented evidence, distinguish scores from contributions, distinguish security from churn, TCN-not-run instruction, device/IP change caveat, JSON-only output |
| **User** | Compact normalized evidence JSON (identity, risk, event metadata, session behavior, fusion scores/contributions, triggered rules, sequence evidence, tabular evidence, attribution, churn context) + derived helper facts (top contributors sorted, TCN status, large response bytes, device/IP change flags, failure flags, rules count, confidence label, context-only model list) + required JSON output schema |

The prompt requests a structured JSON response with these fields:

| Field | Type | Description |
|-------|------|-------------|
| `summary` | string | 4-6 sentence analyst summary |
| `riskNarrative` | string | Paragraph about final risk score and tier |
| `behaviorNarrative` | string | Paragraph about session behavior |
| `modelNarrative` | string | Paragraph about model scores/contributions/fusion |
| `rulesNarrative` | string | Paragraph about triggered rules |
| `sequenceNarrative` | string | Paragraph about sequence models and TCN |
| `keyEvidenceBullets` | string[] | 5-8 evidence bullets |
| `modelScoreExplanation` | object | Per-model explanations |
| `triggeredRulesExplanation` | object[] | Per-rule explanations |
| `possibleInterpretation` | string | Cautious interpretation |
| `limitations` | string[] | Missing/limiting evidence notes |
| `recommendedActions` | string[] | 3-5 actions |
| `disclaimer` | string | Fixed disclaimer |

This structured output is parsed by `LlmExplanationService` and mapped to `V36LlmExplanationResponse`. All existing frontend fields (`summary`, `evidenceBullets`, `possibleInterpretation`, `recommendedActions`, `modelScoreExplanation`, `disclaimer`) remain present. New optional fields (`riskNarrative`, `behaviorNarrative`, `modelNarrative`, `rulesNarrative`, `sequenceNarrative`, `limitations`, `triggeredRulesExplanation`) are available for the frontend to consume without breaking existing rendering.

##### Request body shape

NVIDIA NIM is an OpenAI-compatible API. All fields are sent as raw top-level JSON — `extra_body` is a Python client concept and is never used in the raw HTTP request.

When `include-extra-body=true`, the request body includes NVIDIA-specific top-level fields:

```json
{
  "model": "nvidia/nemotron-3-super-120b-a12b",
  "messages": [{"role":"system","content":"..."},{"role":"user","content":"..."}],
  "temperature": 1.0,
  "top_p": 0.95,
  "max_tokens": 1800,
  "stream": false,
  "reasoning_budget": 1024,
  "chat_template_kwargs": {"enable_thinking": false}
}
```

When `include-extra-body=false`, only OpenAI-standard fields are sent:

```json
{
  "model": "nvidia/nemotron-3-super-120b-a12b",
  "messages": [{"role":"system","content":"..."},{"role":"user","content":"..."}],
  "temperature": 1.0,
  "top_p": 0.95,
  "max_tokens": 1800,
  "stream": false
}
```

##### Provider error handling

When the active provider returns an error (HTTP 4xx/5xx, timeout, empty response, auth failure), the service:
1. Does **not** store the failed provider result as a successful NVIDIA explanation in Redis or SQL
2. Returns a heuristic fallback with `source=provider_error_fallback`, `fallback=true`, and `provider=heuristic`
3. Does **not** poison the cache — subsequent `forceRefresh=false` calls will attempt the provider again

The previous behavior (storing empty provider failures as cached NVIDIA explanations) was removed.

To switch to a different NVIDIA NIM model, change `app.llm.nvidia.model`. To switch to Gemini, set `app.llm.provider=gemini` and configure `spring.ai.google.genai.api-key`.

##### Diagnostic debug flow

If the provider returns 400, use this step-by-step approach:

1. **Set minimal mode**: `app.llm.nvidia.minimal-request-mode=true`, `include-extra-body=false`, `max-tokens=128`, `log-request-json=true`
2. **Trigger POST explanation** for any event — the provider will send `"Say hello in one sentence."` instead of evidence
3. **Check `LLM_PROVIDER_REQUEST_BODY` log** — compare roles, content lengths, and present fields against a known-working body (e.g., from PowerShell)
4. **Check `LLM_PROVIDER_ERROR` log** for exact NVIDIA error response body — NVIDIA usually names the invalid field
5. **If minimal mode works**, switch to `minimal-request-mode=false` with `include-extra-body=false` and retry the real explanation
6. **If normal mode fails**, reduce evidence size (check `max-evidence-size-kb`) or remove problematic evidence fields
7. **Only after normal mode works**, test `include-extra-body=true` with `reasoning-budget`

Always clear Redis keys (`ai:explanation:v3_6:alert:<eventId>:*`) and SQL rows (`DELETE FROM llm_explanations WHERE event_id = '<eventId>'`) between tests to avoid stale cache hits.

## Session Finalization Metadata

`dataprocessor` supports hybrid session finalization — sessions can be finalized explicitly (logout/SSO disconnect) or implicitly (inactivity timeout, max-open-duration).

### Explicit End Reasons

| Reason | Meaning |
|--------|---------|
| `explicit_logout` | User triggered a logout event (e.g., `Déconnexion`) |
| `explicit_sso_disconnect` | User triggered an SSO disconnect event (`SSO Disconnect`) |

### Implicit End Reasons

| Reason | Meaning |
|--------|---------|
| `inactivity_timeout` | Session idle time exceeded `app.session.finalization.inactivity-timeout-seconds` |
| `max_open_duration` | Session total open duration exceeded `app.session.finalization.max-open-duration-seconds` |

### Important

- Timeout finalization is a lifecycle closure mechanism, not automatically an anomaly.
- The existing `session_timeout` rule evidence (from `app.rules.session-timeout.threshold-seconds`) remains separate.
- Timeout-closed sessions still produce SQL rows, Redis investigation payloads, and contribute to dashboards.

### Where the fields appear

- **Alert Investigation** (`GET /api/v1/alerts/{eventId}`): the flat fields `sessionEndReason`, `sessionEndedExplicitly`, `sessionEndedAt`, `sessionDurationMs`, `sessionEventCount` are stored in the investigation payload JSON by `dataprocessor`. The API maps them into a `sessionLifecycle` object when present.
- **Runtime Health** (`GET /api/v1/ai/runtime-health`): `sessionFinalization` counters appear when the `dataprocessor` has written them to the health snapshot.
- **Diagnostics** (`GET /api/v1/security/diagnostics`): `sessionFinalization` counters are available inside the embedded `runtimeHealth`.
- **Live Alerts** (`GET /api/v1/alerts/live`): optional `sessionEndReason` and `sessionEndedExplicitly` fields may appear when present in the Redis snapshot.

All session finalization fields are optional and null-safe. Missing fields do not cause errors.
